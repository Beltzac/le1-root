# LE1 fixes — 2026-09-10 — root + clock boot persistence

## The two real problems

1. **Freezing / rarely works (root).** The exploit is a timing race that lands
   root ~1 in 3 runs. Every miss could park the parent in `readv()` forever (or
   fault the kernel), and the MTK watchdog then reset the SoC — the observed
   "freeze". It was made worse by a boot-time *loop* re-running the exploit
   (`root-loop.sh`) and by `fsync()` on every log line against a slow eMMC.
2. **Does not stick on boot.** After a successful run, root was gone after
   reboot. The `sudaemon.rc` / `timefix.rc` files were on `/system` and correct,
   but nothing started at boot (`init.svc.sudaemon` empty, `le1-loadtime.log`
   stale). The 2026-09-06 session concluded "this MTK init ignores custom
   `/system/etc/init/*.rc`". **That conclusion is not confirmed** — see
   "Bootloader evidence" below — so the fix does not depend on it either way.

## The fix

### Bootloader evidence (why the "init ignores rc" story is shaky)
`lk.bin` (the bootloader that builds the kernel cmdline) contains
`androidboot.init_rc=%s` but only ever formats it with
`/vendor/etc/init/hw/meta_init.rc` or `/vendor/etc/init/hw/factory_init.rc`.
So in **normal** boot `ro.boot.init_rc` is empty and AOSP init parses both
`/init.rc` and (in second stage) `/system/etc/init`. The deterministic hook is
still the ramdisk one — but a custom rc *should* also work, so the on-device
failure was probably the service itself not coming up, not the parser.

### VM verification (2026-09-10)
- `test/test-persist.sh` runs the real `persist.sh` + `install-recovery.sh` +
  `le1-boot.sh` + `verify-boot.sh` inside an **Alpine Linux rootfs under proot**
  with a fake `/system` and `/vendor`. Verifies: default install writes the
  vendor hook and leaves `install-recovery.sh` untouched; the boot supervisor
  starts sudaemon, attempts the clock restore, enforces auto_time/ntp, writes
  the cache; `--with-recovery-hook` backs up the stock script; `verify-boot.sh`
  reports the live hook. **ALL PASS.**
- `test/test-toybox.sh` extracts the unit's own `toybox` + `mksh` + bionic libs
  from `system.img` and runs the scripts under `qemu-arm`. Proves the device
  shell parses them (`mksh -n`), the applet matrix works, and — critically —
  that toybox `date -u @EPOCH` is the SET form (a data point busybox gets
  wrong). **ALL PASS.**
- `test/test-boot.sh` unit-tests the supervisor with stubs. **ALL PASS.**
- The unit's `init` itself was run under `qemu-arm`/proot with the SELinux
  policy extracted from `system.img`; it gets through first-stage mounts and
  policy load, but proot cannot provide a writable `selinuxfs`, so Android's
  PID1 boot cannot be completed in-VM to observe the rc parse.

### Boot hook (the deterministic path)
Default hook: **`/vendor/etc/init/le1-boot.rc`**. Android init parses
`/vendor/etc/init` unconditionally in second stage, and — unlike
`/system/etc/init` — it is not gated by `ro.boot.init_rc`. Crucially, this does
NOT overwrite a stock system file: the previous (2026-09-06) approach replaced
`/system/bin/install-recovery.sh`.

`post-root/persist.sh` installs:

- `/vendor/etc/init/le1-boot.rc` — `service le1boot /system/bin/le1-boot.sh vendor-rc`
  (class main, user root) + `service sudaemon` + a `sys.boot_completed` trigger;
- `/system/etc/init/sudaemon.rc` — belt-and-suspenders in case `/system/etc/init`
  *is* parsed;
- `/system/bin/le1-boot.sh` — the supervisor;
- `/system/bin/verify-boot.sh` — reports which hook actually fired.

Opt-in fallback (only with `persist.sh --with-recovery-hook`): install
`/system/bin/install-recovery.sh` (the ramdisk `flash_recovery` service), with
the stock script preserved as `install-recovery.sh.stock`.

`le1-boot.sh` is a **supervisor that never exits**. It:

- restores the cached clock immediately (dead RTC → 2009 → TLS invalid),
- starts/keeps `/system/bin/sudaemon` running (`su_ok` poll),
- keeps Android `auto_time=1` (vendor resets it on cold boot),
- refreshes `/data/misc/le1-time/last` only when it moved >30 s (eMMC wear),
- takes a single-instance lock (two hooks installed ⇏ two supervisors),
- logs the hook tag so `verify-boot.sh` can say which path fired.

### deploy.sh no longer fires the exploit blindly
`./deploy.sh` now checks `su -c id` first. If root is already active it skips
the exploit entirely and just re-asserts persistence; `--force-exploit`
overrides. One less pointless kernel race.

Offline tests: `bash test/test-boot.sh` (stub unit test), `bash test/test-persist.sh`
(Alpine/proot VM), `bash test/test-toybox.sh` (device toybox/mksh under qemu-arm)
→ all pass.

### No more exploit hammering
`root-loop.sh` (repo: `boot/root-loop.sh`) now:
1. exits immediately if `su` already works (just re-asserts persistence),
2. exits if the boot hook + `sudaemon` are installed (the hook restores root),
3. otherwise runs at most `MAX_ATTEMPTS` (default 3) with a hard `timeout 120`.

### Exploit hardening (`exploit/le1_root.c`)
- `clobber_data`: `SIGALRM` (4 s, no `SA_RESTART`) around the blocking `readv`,
  so a missed race aborts the attempt instead of hanging the unit.
- `clobber_with_retry`: 40 → 24 attempts + 30 ms cooldown (bounded worst case).
- `message()`: `fsync(2)` throttled to 1-in-8 (slow-eMMC I/O stall).
- After install, runs `$HOME/.le1/persist.sh` to install the boot hook.

### Termux:Boot fallback (`boot/20-autotime.sh`)
Preferred path is now root (`su -c`). The adb path is bounded: one
`adb connect`, at most one `ctl.restart adbd`, then give up — no 40-iteration
loop, no restart storm. (The adb hack was what "kept freezing" at boot.)

## Deploy
```bash
./deploy.sh          # stages everything, then: persist if su works, else exploit
./deploy.sh --force-exploit   # force the exploit even if root is live
```
The exploit only has to succeed once. After that root + correct clock come back
on every boot with no exploit and no adb.

## Verify after reboot (when online)
```bash
ssh ... 'sh ~/.le1/verify-boot.sh'     # reports which hook is live + su + clock
ssh ... 'getprop init.svc.le1boot; getprop init.svc.sudaemon; su -c id; date -u'
cat /data/misc/le1-time/boot.log       # supervisor log (hook tag)
```
`verify-boot.sh` prints a one-line verdict (vendor hook / recovery hook /
secondary only / none). If it says none, the ROM ignores `/vendor/etc/init` — fall
back to `persist.sh --with-recovery-hook` (ramdisk `flash_recovery`), then to the
Magisk `boot.img` path.
