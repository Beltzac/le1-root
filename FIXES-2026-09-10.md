# LE1 fixes — 2026-09-10 — root + clock boot persistence

## The two real problems

1. **Freezing / rarely works (root).** The exploit is a timing race that lands
   root ~1 in 3 runs. Every miss could park the parent in `readv()` forever (or
   fault the kernel), and the MTK watchdog then reset the SoC — the observed
   "freeze". It was made worse by a boot-time *loop* re-running the exploit
   (`root-loop.sh`) and by `fsync()` on every log line against a slow eMMC.
2. **Does not stick on boot.** Even after a successful run, root was gone after
   reboot. Root cause (verified on-device): **this MTK init silently ignores
   custom `/system/etc/init/*.rc`** — after reboot `init.svc.sudaemon` is empty
   and the loadtime log is stale, although the `.rc` was written correctly. So
   the daemon never auto-started; only the files persisted, not the process.

## The fix

### Boot hook (the thing that actually works on this init)
The stock **ramdisk** `init.rc` (always parsed) defines:

```
service flash_recovery /system/bin/install-recovery.sh
    class main
    oneshot
```

`post-root/persist.sh` replaces `/system/bin/install-recovery.sh` with a
launcher that `exec`s `/system/bin/le1-boot.sh`. The stock file is preserved
once as `install-recovery.sh.stock`.

`le1-boot.sh` is a **supervisor that never exits** — required because init
SIGKILLs the process group of a `oneshot` service as soon as its main process
exits, so a "spawn and return" hook would have its children killed. It:

- restores the cached clock immediately (dead RTC → 2009 → TLS invalid),
- starts/keeps `/system/bin/sudaemon` running (`su_ok` poll),
- keeps Android `auto_time=1` (vendor resets it on cold boot),
- refreshes `/data/misc/le1-time/last` every 60 s so the next boot starts near-correct,
- adds a belt-and-suspenders `/system/etc/init/sudaemon.rc` in case a future
  build does honour it.

Offline test: `bash test/test-boot.sh` (stubs date/settings/su/sudaemon) → all pass.

### No more exploit hammering
`root-loop.sh` (repo: `boot/root-loop.sh`) now:
1. exits immediately if `su` already works (just re-asserts persistence),
2. exits if the boot hook + `sudaemon` are installed (the hook restores root),
3. otherwise runs at most `MAX_ATTEMPTS` (default 3) with a hard `timeout 120`.

### Exploit hardening (`exploit/le1_root.c`)
- `clobber_data`: `SIGALRM` (4 s, no `SA_RESTART`) around the blocking `readv`,
  so a missed race aborts the attempt instead of hanging the unit.
- `clobber_with_retry`: 40 → 24 attempts + 30 ms cooldown (bounded worst case).
- `message()`: `fsync(2)` throttled to 1-in-8 (slow-eMMC I/O stall).
- After install, runs `$HOME/.le1/persist.sh` to install the boot hook.

### Termux:Boot fallback (`boot/20-autotime.sh`)
Preferred path is now root (`su -c`). The adb path is bounded: one
`adb connect`, at most one `ctl.restart adbd`, then give up — no 40-iteration
loop, no restart storm. (The adb hack was what "kept freezing" at boot.)

## Deploy
```bash
./deploy.sh          # stages sudaemon, exploit, .le1/{persist,le1-boot,install-recovery}.sh; runs once
```
One successful run installs the hook. After that, root + correct clock come back
on every boot with no exploit and no adb.

## Verify after reboot (when online)
```bash
ssh ... 'getprop init.svc.flash_recovery; getprop init.svc.sudaemon; su -c id; date -u'
cat /data/misc/le1-time/boot.log      # supervisor log
```
`init.svc.flash_recovery: running` = hook alive. If it is empty, the device's
ramdisk init.rc differs — fall back to appending the service to an rc the ROM
does parse (or the Magisk `boot.img` path).

## Untested (device was offline)
- `flash_recovery` actually starting our script on the *device's* ramdisk
  (our local ramdisk is the Oct-2025 dump; the unit is the Aug-2020 build).
- `persist.sh` end-to-end on-device (shell syntax checked, not executed).
- `settings` accepting `put global auto_time` as root at class-main time
  (the 60 s supervisor re-tries until system_server answers).
